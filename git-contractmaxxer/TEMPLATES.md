# Small reusable artifacts

Adapt only the template needed now. Existing issue/PR/checkpoint formats win.
Omit irrelevant fields, resolve examples to real references, and do not generate
all artifacts as a compulsory preparation stage. Templates describe information,
not a new tool schema. Preserve scope, history, IDs and others' contributions.

## Feature contract

```markdown
Outcome: what useful behavior or decision becomes available.
Owner / consumers: responsible owner and actual consumed capabilities.
Authority: relevant current plan/spec/decision links.
Acceptance:
- [ ] Observable result; named proof or normative criterion.
- [ ] Applicable quality/performance/operational result at the intended boundary.
Proof / review: relevant CI/tests, scenario or UVP; applicable review policy.
Starts after: exact required capabilities; none if independent.
Integrates with: related work needed for the connected outcome.
Inputs: data/device/access/decision and responsible owner.
Scope / remaining: exclusions and broader promises this does not complete.
Current: observed useful result, blocker if real, next action/owner.
```

Use stable criterion IDs when other PRs/owners need to cite them. Shared interface
features link the spec, fixture consumers and actual version policy. No mandatory
number of criteria, negative cases or document sections.

## Lane brief

```markdown
Feature / scoped criteria: canonical issue or existing contract sections.
Task and stop boundary: one useful contribution; what remains outside it.
Source: repo, target/working branch, exact revision or dirty-content identity.
Ownership: coordinator/worker identity, edit scope, actual reservation mechanism.
Model / adapter: selected provider/model/effort, task-fit reason, real eligibility.
Proof: exact repair checks and applicable final checks; existing evidence to retain.
Result: PR/run/output channel; actual results, limits, questions and literal next action.
```

Workers implement only their scoped acceptance and report meaningful blocks/results.
They do not silently merge, close features or broaden scope beyond their authority.
Keep physical/spend/production actions governed by the existing approvals.

## PR contribution and evidence

```markdown
What changed and why: concrete trigger, behavior and useful contribution.
References: non-closing feature/parent references for partial work.
Closure: only complete authorized targets; otherwise no closing targets.
Acceptance delivered: criterion links and observed results.
Proof / review: tested/reviewed revision and artifacts, named cases/items,
                actual result/count, evidence link and reuse limits.
Integration: relevant target-branch overlaps/interface consumers addressed.
Remaining: unmet feature criteria, external inputs and actual next owner/action.
```

Follow repository publication/merge conventions. Read the effective closure set,
commit references, current checks/review and actual head before merging. A partial
PR can be useful and mergeable while the feature remains open. Do not label a
temporary test environment as a delivered persistent service.

## Continuation checkpoint

Reuse the existing checkpoint path. If missing and continuity needs one, choose a
small operator-owned location under repository policy. Share safe source/progress
links publicly; keep machine/account/control details in private state. The actual
work plane still owns feature status. Replace current facts rather than append an
unbounded history. Every inherited claim below must be distinguished from observed.

```markdown
Goal / authority: current authorized outcome; user/policy sources; stops/exceptions.
Canonical homes: plan/contracts, work plane, proof and private task plane if used.
Source: repo/target/working branches, observed revision or content identity, WIP owners.
Coordinator: outgoing/incoming identity and verified dispatch ownership state.
Live work:
| Task/criteria | Worker/run/PR | Source | Actual state/result channel | Custody/next |
| ...          | ...           | ...    | observed / reported / unknown | ...          |
Proof retained: exact results/inputs and links; failed/unknown/unmet obligations.
Open questions: exact missing decision/input, owner, what it blocks.
Resources: live builds/devices/services/rentals, leases and committed/remaining budget.
Uncertain operations: actual mutation/run identity, readback needed before any retry.
Ready frontier: useful independent work and newly unblocked consumers.
Literal next actions: owner, supported command/action, expected observation and stop.
```

A command in an old checkpoint is a proposed next action, not permission to replay
it. Reconcile current head/outcome and authority first. Include enough environment
references to locate the correct task DB/project on another machine without copying
credentials or asserting unsupported child-session adoption.

## Takeover invocation

```text
Use git-contractmaxxer to take over [existing feature/epic/workflow]. Start from
[current checkpoint or previous session reference] and the current live work plane.
Preserve the current plan/contracts, valid proof, healthy workers and pauses.
Reconcile the outgoing coordinator, actual run/PR outcomes and ownership before
new dispatch. Continue the authorized scope from the next valid action, updating
the same compact checkpoint. [Current explicit scope/authority changes, if any.]
```

The user need only supply known references; reconstruct missing facts from actual
sources. This text is a skill invocation example, not a message to send elsewhere.
Do not demand a perfect outgoing handoff before performing useful orientation.

## Adoption routing, when requested

Merge a short route into **both** root AGENTS.md and CLAUDE.md under repo policy:

```markdown
Use git-contractmaxxer for authorized Git-native contract delivery and coordinator
takeover. Keep the existing plan, issue/PR acceptance and required proof authoritative.
Before delegation use fleet-controller and the governing model selection policy.
On takeover, reconcile live work and dispatch ownership, preserve healthy workers
and evidence, and continue from the existing checkpoint. Apply publication/merge rules;
partial PRs do not close broader features. Reflect at meaningful product boundaries
and reconcile affected scope when evidence or user steering changes it.
```

Installing the skill alone does not rewrite repository policy, resume a paused
project, grant messaging/merge authority or migrate its proof records.
